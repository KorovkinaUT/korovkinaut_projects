# Link Tracker

Link Tracker — это приложение для отслеживания обновлений по ссылкам и отправки уведомлений в Telegram. Проект состоит из Telegram-бота и сервиса, который хранит отслеживаемые ссылки, периодически проверяет появление обновлений и отправляет уведомления пользователю.

## Возможности

- Telegram-бот для управления отслеживаемыми ссылками
- Поддержка GitHub и Stack Overflow
- Диалоговое добавление ссылок с тегами
- Периодическая проверка обновлений ссылок
- Хранение данных в PostgreSQL
- Кэширование списка ссылок в Valkey
- Отказоустойчивая доставка уведомлений через HTTP и Kafka
- Интеграция с AI Agent
- Unit и интеграционные тесты

## Используемые технологии

- Go
- PostgreSQL
- Valkey
- Kafka
- docker-compose

- goqu

## Реализация

### 1. Telegram-бот

Поддерживаемые команды:

| Команда | Описание |
| ------- | -------- |
| `/start` | регистрация пользователя в системе |
| `/help` | вывод списка доступных команд |
| `/track` | добавить ссылку для отслеживания, поддерживаются теги для ссылок |
| `/untrack` | удалить ссылку из отслеживания |
| `/list` | показать отслеживаемые ссылки |

Команды подключаются через набор handlers, а маршрутизация сообщений реализована через dispatcher.

### 2. Диалог добавления ссылки

Поддерживается добавление ссылки для отслеживания в формате диалога:

1. пользователь вводит команду `/track`;
2. бот переводит пользователя в состояние ожидания ссылки;
3. пользователь отправляет URL;
4. бот переводит пользователя в состояние ожидания тегов для ссылки;
5. пользователь вводит теги или `/cancel` для добавления без тегов;
6. ссылка передаётся в scrapper-сервис;
7. бот завершает сценарий.

Для этого используется отдельная сущность состояния пользователя, которая позволяет хранить текущий шаг диалога для каждого chat id.

### 3. Управление ссылками

Бот взаимодействует со **scrapper-сервисом** через HTTP API.

Поддерживаемые операции:

- регистрация чата;
- добавление ссылки;
- удаление ссылки;
- получение списка ссылок.

### 4. Проверка обновлений

Реализован компонент **checker**, который отвечает за периодическую проверку обновлений ссылок. Он запускается по расписанию через **scheduler**, обрабатывает ссылки батчами и поддерживает параллельную проверку обновлений.

Общий алгоритм работы **checker**:

1. получить батч отслеживаемых ссылок;
2. запустить workers для обработки ссылок;
3. определить тип каждой ссылки;
4. получить новые события через соответствующий клиент;
5. сформировать уведомления о новых событиях и отправить их;
6. обновить информацию о последней проверке ссылки;
7. сформировать сообщения об ошибках обработки и отправить их.

Реализовано отслеживание обновлений следующих сайтов:

- **GitHub**;
- **Stack Overflow**.

Архитектура построена на интерфейсах, что позволяет легко добавить поддержку новых источников обновлений.

### 5. Хранение данных

Данные хранятся в базе данных **PostgreSQL**.

Используется следующая схема:

- `chats` — зарегистрированные пользователи;
- `links` — отслеживаемые ссылки;
- `link_chat` — подписки чатов на ссылки;
- `link_tag` — теги ссылок, заданные пользователем.

Одна ссылка хранится в базе только один раз независимо от количества пользователей, поддерживается каскадное удаление и используются индексы для ускорения запросов.

Доступ к базе данных реализован через паттерн **Repository**.

Поддерживаются две реализации (настраивается через конфигурацию):

- `SQL` — работа через raw SQL;
- `GOQU` — работа через query builder.

Фабрика репозиториев создаёт необходимую реализацию в зависимости от конфигурации приложения.

Все операции с ссылками (`AddLink`, `RemoveLink`) выполняются в рамках транзакций.

### 6. Кэширование

Для ускорения обработки запроса `GET /list` реализовано кэширование результатов в **Valkey**.

Особенности реализации:

- при повторном запросе данные возвращаются из кэша без обращения к базе данных;
- при добавлении или удалении отслеживаемых ссылок кэш автоматически инвалидируется;
- время хранения записей в кэше настраивается через конфигурацию.

Дополнительно реализовано **Client Side Caching** на стороне клиента Valkey, что позволяет повторно использовать недавно полученные данные без сетевого обращения к серверу при сохранении корректной инвалидации кэша.

Для обеспечения отказоустойчивости используется кластер **Valkey**, состоящий из трёх master-нод и трёх replica-нод.

### 7. Отказоустойчивость

Для повышения надёжности взаимодействия между сервисами реализованы следующие механизмы:

- **Timeout** — ограничение времени выполнения HTTP-запросов;
- **Retry** — повторное выполнение запросов при временных ошибках с фиксированным интервалом между попытками;
- **Circuit Breaker** — автоматическое прекращение обращений к недоступным сервисам с последующим переходом в режим проверки восстановления;
- **Rate Limiting** — ограничение количества запросов к публичным HTTP endpoint'ам с одного IP-адреса;
- **Fallback** — при недоступности HTTP уведомления автоматически отправляются через Kafka;
- **Dead Letter Queue (DLQ)** — сообщения, которые не удалось обработать после заданного количества попыток, автоматически помещаются в отдельный Kafka topic для последующего анализа.

Для Kafka consumer реализована повторная обработка сообщений. Ошибки десериализации и валидации считаются неретраимыми и сразу отправляются в **DLQ**, а ошибки обработки сообщений повторно обрабатываются с экспоненциально увеличивающейся задержкой между попытками. После исчерпания количества попыток сообщение также помещается в **DLQ**.

Все параметры механизмов отказоустойчивости настраиваются через конфигурацию приложения.

### 8. AI Agent

Подготовлена интеграция с AI-сервисом для обработки обновлений перед отправкой уведомлений пользователю.

Архитектура построена на интерфейсе **Agent**, что позволяет использовать различные реализации AI-провайдеров без изменения остальной логики приложения.

Обработка уведомлений выполняется следующим образом:

1. **Scrapper** публикует сырые обновления в **Kafka**.
2. **AI Agent** получает сообщения и выполняет их обработку.
3. Обработанные уведомления публикуются в отдельный **Kafka topic**.
4. **Bot** получает итоговые сообщения и отправляет их пользователю.

В текущей версии проекта реализован **Stub Agent**, который используется вместо реальной LLM и позволяет протестировать полный сценарий взаимодействия между сервисами. Архитектура и точки интеграции подготовлены для последующего подключения полноценного AI-провайдера.

Использование AI Agent настраивается через конфигурацию приложения.

### 9. Тесты

Реализованы unit-тесты для проверки работы основных компонентов системы и интеграционные тесты для проверки совместной работы различных компонентов. Интеграционные тесты используют **Testcontainers** для запуска PostgreSQL, Kafka и Valkey.

## Конфигурация

### .env файл

Перед запуском необходимо создать файл `.env` в корне проекта (пример есть в `.env.example`).

Минимально необходимая переменная окружения:

```env
APP_TELEGRAM_TOKEN=your_token
```

Остальные параметры можно не указывать — будут использованы значения по умолчанию.
